Lab 34: Bio, filtered by a naive filter

Source: location.searchSink: innerHTML (naive filter)mXSS family

What is happening

The filter here blocks anything matching <(script|img|svg|iframe)\b as the first tag in the string, a quick denylist someone might reach for without thinking too hard about it. It then inserts whatever gets past that check with innerHTML.

The payload

<noscript><img title="</noscript><img src=x onerror=alert(1)>"></noscript>

Read as text, this looks like one harmless element, <noscript>, containing one <img> whose title attribute happens to contain some literal angle brackets. That's exactly how the filter above reads it too: first tag is noscript, not on the denylist, let it through.

That is not how the browser reads it

<noscript>, like <style>, <script>, <iframe>, <xmp>, <title>, <textarea>, <noembed>, and <noframes>, has a special content model in the HTML spec: everything inside is raw text, not markup. The browser does not know or care that title=" looks like it opened a quoted attribute. It just scans forward for the literal next </noscript>, finds it immediately, and ends the element right there, regardless of where it appears. Everything after that, <img src=x onerror=alert(1)>">, is parsed as ordinary markup: a real <img> tag with a real onerror attribute, something the filter above never saw.

PortSwigger's cheat sheet lists this family under names like "noscript consuming tag" and "style consuming tag" — the element consumes everything up to that embedded fake closing tag, no matter how deeply it looks nested in the source text.

This is mXSS, with a caveat

<noscript>'s raw-text behaviour above is exactly the mechanism behind real, named mutation XSS vulnerabilities: Mozilla's HTML-sanitizing library Bleach had this as a CVE (CVE-2020-6802, "mutation xss in <noscript> handling"), and so did the browser's own DOMParser API (CVE-2021-23974, "potential XSS via noscript tags parsed by DOMParser APIs"). The pattern in both: something that checks untrusted HTML parses <noscript> one way, and whatever finally inserts it parses that same markup a different way, with no shared understanding of the raw-text rule between the two.

We tested that exact divergence directly in this browser, rather than assume it still holds. DOMParser here genuinely does treat <noscript> differently from innerHTML: it parses this payload's content as an ordinary quoted attribute, not raw text, matching the CVE's premise. But a sanitizer that uses DOMParser to check untrusted HTML has to serialize its cleaned result back into a string before handing it to the real sink, and that serialization step HTML-encodes the </> characters our payload needs — so by the time this particular string reaches a real innerHTML assignment, there's no literal closing tag left to consume, and nothing survives the round trip. The divergence is real and verified; this specific payload doesn't happen to be the one that survives it.

What this lab demonstrates end to end, fully verified, is the simpler half of that story: the raw-text mechanism itself defeats a filter that pattern-matches text instead of parsing it as real HTML. That's true on its own, with no sanitizer or second parse involved at all, which is also why it was straightforward to confirm firing in a real browser.

Fix

Don't pattern-match HTML as text. Parse it properly and inspect the result, the way lab 28's DOMPurify does, or avoid HTML entirely with textContent.
