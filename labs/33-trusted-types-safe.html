Lab 33: Bio, with Trusted Types enforced (safe)

Source: location.searchSink: innerHTML (blocked by Trusted Types)

What is happening

This page has the exact same vulnerable-looking line as lab 01: profile.innerHTML = bio, a raw string, no sanitizing. But its Content-Security-Policy includes require-trusted-types-for 'script'. Submit the usual payload and look at the status line: the assignment itself throws, and nothing is ever inserted.

Why this is different from CSP's script-src

Lab 31's CSP let the innerHTML assignment succeed, then stopped the result (the inline onerror) from running. Trusted Types works earlier: with it required, browsers only accept a plain string for innerHTML, src, and a handful of other sinks if the page has no policy for them, or a specific object (a TrustedHTML) in place of a string if it does. No policy means no plain strings allowed, full stop, so the line throws before the browser's HTML parser ever sees the payload. That closes the gap lab 32 showed: no HTML is parsed from an unchecked string at all, so there's no attribute left dangling to exploit.

Try this 
<img src=x onerror=alert(1)>

The status line below the form shows the real TypeError the browser throws.

How you'd actually use innerHTML on a page like this

Define a policy that only accepts a string you've sanitized, and use the policy to create the value instead of a plain string: 

const policy = trustedTypes.createPolicy('default', {
  createHTML: (dirty) => DOMPurify.sanitize(dirty)
});
profile.innerHTML = policy.createHTML(bio); // a TrustedHTML, not a string

This is DOMPurify from lab 28 again, now paired with a browser-enforced guarantee that nothing else on the page can skip the sanitizing step, even by accident.
