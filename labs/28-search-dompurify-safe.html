Lab 28: Bio, sanitized (safe)

Source: location.searchSink: innerHTML (sanitized with DOMPurify)

What is happening

This is the fixed version of lab 01. The value still goes to innerHTML, the same sink, but it's passed through DOMPurify.sanitize() first. DOMPurify parses the string, walks the resulting tree, strips anything dangerous (script tags, event handler attributes, javascript: URLs, and more), and gives back a clean string that's safe to insert.

Why this is the realistic fix

textContent (the fix shown in lab 01) is the right answer when you only ever need plain text. DOMPurify is for the case every other framework's "safe HTML" fix in this hub pointed to but didn't show: when you genuinely need to render some HTML from a user, like a rich-text bio or comment with bold and links, and plain text would be too limiting. It's the library most real-world apps reach for, usually alongside a framework's own bypass-the-sanitizer escape hatch (v-html, dangerouslySetInnerHTML, bypassSecurityTrustHtml, and the rest in this hub) rather than instead of it.

Try to break it

Use any payload from the other labs. They should all come back stripped. Bold text, links, and lists survive; <script>, onerror, and javascript: hrefs don't.

Try this 
<b>bold</b> <a href="javascript:alert(1)">click</a> <img src=x onerror=alert(1)>

The bold text and the link stay (with the javascript: URL removed from the link); the image's onerror is gone.

No sanitizer is a substitute for understanding the sinks in the rest of this hub. DOMPurify itself has had real, patched vulnerabilities over the years, usually mXSS-style parsing edge cases rather than the obvious payloads — this hub originally shipped with DOMPurify 3.2.3, which GHSA-h8r8-wccr-v5f2 (fixed in 3.3.2) affects, and has since been upgraded to a current release while writing this note. Keep it up to date, the way this hub just had to.
