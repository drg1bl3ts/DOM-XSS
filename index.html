DOM XSS Practice Hub

DOM XSS happens when JavaScript takes data from an attacker-controllable source and passes it to a dangerous sink without making it safe. The server is not involved. The bug is entirely in the browser.

These pages are intentionally vulnerable. Run them locally only. Read the sources and sinks notes first, or jump straight into a lab.

Reference

  • Sources: where attacker data comes from
  • Sinks: where that data becomes code

Where you'll actually find these

These patterns aren't tied to one kind of site. The same bug shows up wherever the page has that shape, whether it's a shop, a bank, or a blog.

Where on the pageSites where this shows upWhat's usually going onTry
Search box, "no results for ___" E-commerce, docs sites, blogs, almost anything with a search feature The query is echoed back into the page with innerHTML or a template engine 01, 24, 25
Login page, "session expired" link, post-checkout redirect Banking, SaaS logins, anywhere with an auth flow A returnUrl / redirect / next / callbackUrl query param goes straight into location.href or a link's href 04, 09
Profile page: display name, bio, "about me" Social apps, SaaS dashboards, gaming platforms, forums Saved once, then rendered for every visitor with innerHTML / v-html / dangerouslySetInnerHTML, i.e. stored XSS 06, 22, 23
Any embedded iframe: chat widget, share button, payment form, ad Sites that embed third-party widgets, which is most sites The parent page and the iframe talk over postMessage, often with no check on who sent it 07
The URL after the # Single-page apps: webmail, admin dashboards, banking portals built in Angular/React/Vue The client-side router reads location.hash to decide what to show, no page load involved 03, 13
"Save draft", "continue later", recently-viewed items Blogs, CMS admin, e-commerce The data sits in localStorage and gets rendered back on your next visit 06
Report titles, saved views, anything built from a template behind the scenes Internal admin tools, legacy enterprise software Still commonly built with Handlebars/Mustache or Lodash templates, which don't auto-escape the way newer frameworks do by default 24, 25

Checked against real reports, not just theory: a CVE-level redirect-param bug (Homarr, callbackUrl), postMessage XSS affecting a share button used on over a million sites (Detectify), and PortSwigger's own search-bar DOM XSS walkthroughs.

Mitigations

These labs stop asking "does the payload fire" and start asking "what actually stops it." Each is the real, working sink from an earlier lab with one specific defense added.

LabMitigationWhat it shows
28DOMPurifySanitizing untrusted HTML before innerHTML, instead of avoiding HTML entirely (safe)
31Content-Security-PolicyA real CSP blocking the classic onerror payload (safe, for this payload)
32CSP's blind spotThe same CSP doing nothing against dangling markup injection, which steals data with no script at all
33Trusted TypesThe browser refusing the innerHTML assignment outright, closing the gap lab 32 found (safe)
35Trusted Types + jQuery 4.0A library has to be built for Trusted Types too — jQuery 3.x fails to even load under it (safe)
